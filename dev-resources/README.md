# Dev resources

What this client needs to be worked on without the server repository to hand:
the API contract it talks to, and how to read it.

```
dev-resources/
  api/
    openapi.json        the contract — generated, do not edit
    sync-openapi.mjs    regenerates it from a running server
```

## The contract

`api/openapi.json` is the Plotmap API's own OpenAPI document, generated by the
server from its live code, narrowed to the routes this client calls — 37 paths
out of the product's 137. Admin and internal routes are never included.

```bash
npm run api:sync                        # from http://localhost:9000
npm run api:sync -- http://host:9000    # from somewhere else
```

Re-run it after a backend change and read the diff: that is the point of
keeping it here rather than reading Swagger when you happen to remember to.
The script finds the routes by scanning `src/` for `/api/v1/…` literals, so a
new call appears in the contract as soon as the code makes it.

## Conventions the document does not tell you

**Base URL.** No `servers` block: the host is the client's business, resolved
in `src/lib/api.ts` (environment variable, else the machine that served the
bundle, else localhost). Every path is under `/api/v1/`.

**Auth.** A Bearer JWT from the OTP flow — `POST /auth/otp/request` then
`POST /auth/verify`. `src/lib/auth.tsx` holds it in `expo-secure-store` and
`request()` attaches it.

**The envelope is not uniform.** Most routes wrap `{ data, errors, meta }`;
auth and session routes return the resource directly, or `{ error }` on
failure. `request()` normalises both — go through it rather than `fetch`.

**The server formats, the client renders.** Money, addresses and field labels
arrive ready to display (`displayPrice`, `markerPrice`, `addressDisplay`,
`highlightFields`). Formatting them again on the client duplicates work and
drifts from the web app.

## Where the document is thin

`POST /listings/map` — the marker feed — has no response schema in the
generated document (the server returns untyped JSON there). Verified against a
running server, it answers:

```jsonc
{
  "listings": [ /* a mix of two shapes */ ],
  "total": 1077,      // listings matching the query, not rows returned
  "binned": true,     // true once the server grouped them
  "sampled": false
}
```

A lone listing:

```jsonc
{ "id": "...", "coordinates": { "latitude": 0, "longitude": 0 }, "markerPrice": "₹ 42.0 L" }
```

A bin, which is not a listing — it has no single price and nothing to open:

```jsonc
{
  "id": "bin:570:92",
  "coordinates": { "latitude": 0, "longitude": 0 },
  "count": 4,
  "bbox": { "south": 0, "west": 0, "north": 0, "east": 0 },
  "mode": "sale",
  "priceLo": "₹ 1.1 L",  "priceHi": "₹ 67.0 L",
  "priceLoAmount": 110000, "priceHiAmount": 6700000,
  "samples": [ /* up to 3 member listings, in the lone-listing shape */ ]
}
```

The server bins above roughly 500 points, so the same request answers in
either shape depending on how much is in view — a client reading this feed has
to handle both. `dev-data.mapFeed` mirrors it (returning two samples per bin
rather than three), which is how it can be exercised with no server running.

**This client does not call that feed.** The map draws the first 60 rows of
`POST /listings/search`, which is why it never shows more than 60 markers.
